# 简历、改造贡献与面试材料

适用目标：AI 应用 / Agent 开发。更新：2026-10-08。内容来自当前仓库和实际验证；使用前应能现场解释对应代码。

## 项目名称与定位

**多 Agent 电商导购与证据核验系统｜开源项目二次开发**

技术栈：Python、FastAPI、LangGraph、SQLite / SQLAlchemy、BM25、向量检索、RRF、百炼 Embedding、pytest、GitHub Actions。

本项目基于 bcefghj/multi-agent-ecommerce-system 学习改造；当前 Python 导购实现、评测和展示与上游多语言教学链路分开。开发中使用了 AI 编程辅助。简历中的“设计/实现”应对应你确实理解、参与并能修改的部分，不把上游原有实现写成完全独立原创。

## 可用的三条简历表述

- 基于开源教学项目改造 Python 电商导购服务，使用 FastAPI + LangGraph 编排商品、FAQ 和混合路线，接入 SQLite 会话及来源版本管理，实现推荐前价格、库存与明确条件核验，并返回引用和工具执行轨迹。
- 实现 BM25、向量及 RRF 混合检索，接入百炼 text-embedding-v4；采用延迟建索引、版本失效与故障回退机制，主接口合成场景验证 8/8 通过、17 次真实 HTTP 成功，区分请求模式与实际执行模式。
- 建立冻结合成题集、检索/完整集合/引用核验评测和 CI 门禁；324 项测试及四套质量门禁通过。32 题检索对比中 BM25 与百炼混合 MRR@5 为 0.8948 / 0.9310，该结果仅限合成资料，保留纯向量低于 BM25 的结果与误差分析。

## 两分钟讲解稿

“我从一个多语言电商 Agent 教学项目开始，重点改造 Python 导购链路。需求分成商品推荐、FAQ 和混合问题，由 LangGraph 路由到不同职责的角色。结构化数据库负责价格和库存，RAG 从商品资料和 FAQ 里找支持材料，返回前再检查当前来源和明确条件。

我重点处理了无证据补推荐、来源过期、检索故障和执行模式不透明的问题：推荐数量只作上限，向量失败明确回到 BM25，并在响应里记录实际模式。真实百炼已经接入主接口，8 个合成场景全部通过，另有 324 项测试和四套冻结门禁。

这些数据仍是合成资料，标签主要由代理编写并经代码审计；它证明流程可复现，不能代表真实商品或线上业务效果。下一步需要授权商品资料、真人标注与开放表达评测。”

## 面试追问与回答要点

1. **为什么要 RAG，数据库不够吗？** 数据库处理价格/库存等结构化事实；描述、评价与 FAQ 的支持材料需要检索。证据不能覆盖数据库事实。
2. **多 Agent 与普通工作流有什么区别？** 本项目是明确输入输出契约的职责拆分和 LangGraph 条件路由，默认模板回答；可以解释哪些节点并行、哪些依赖，不能声称四个自主 LLM 协商。
3. **为什么混合检索？** 词面精确条件对 BM25 有利，语义向量可补表达差异；RRF 融合排名。当前合成集纯向量 MRR 0.7902 低于 BM25，混合 0.9310，不能概括所有业务都提升。
4. **如何证明证据可信？** 核对商品主体、当前 source_id/版本、数据库快照与原文片段。来源真伪和自由文本语义仍需人工及上游数据保障。
5. **为什么不是每次都调用 embedding？** BM25 不需要；云索引首次实际需要时建立，同版本复用。来源变化后失效。构建失败缓存，避免每问重复收费。
6. **超时线程还在运行怎么办？** 等待超时与后台网络线程完成不是一回事；响应只复制已完成的请求局部诊断，恢复动作及晚完成行为都有测试。
7. **A/B 证明收益了吗？** 没有。实现的是分桶、归因、降级统计和回放，缺真实流量与实验周期，不能报告 CTR 或 GMV 提升。
8. **满分是否过拟合？** 多组题首次成绩和按失败题修复后的同题复测分开保存；调优满分只作回归，不能当独立泛化。
9. **哪些是你做的？** 按台账指向改造代码与真实提交，现场解释一处错误、定位方式、失败测试和修复。AI 辅助不替代理解。
